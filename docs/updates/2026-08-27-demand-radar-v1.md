# 2026-08-27 仙策需求雷達 V1

## 2026-08-28 流量訊號完整性 V2

V1 的事件漏斗保留，但修正兩個不應跨越的證據界線：瀏覽器工作階段不等於真人，無法確認來源的工作階段也不等於陌生客戶。2026-08-29 00:00（台北）以前的事件繼續保存在資料庫供稽核，但不再進入需求雷達與營運結論。

- 一般公開流量分為可歸因與未歸因工作階段；前者只代表粗粒度來源可辨識，不代表身分已辨識。
- 管理員從已登入後台的「官網預覽」進入，伺服器才在簽章 Session 設定八小時 `admin-preview` 分類；公開網址參數無法自行取得排除資格。
- 後台、需求雷達與每日摘要統一使用「公開工作階段／仙策工作階段」，另列管理測試、機器與舊基準排除量。
- 流量來源改數不重複工作階段，不再把同一工作階段的多個事件誤加為多人。
- 不新增 IP、瀏覽器指紋、跨站 Cookie 或第三方追蹤；所有既有隱私與安全邊界維持不變。

完整決策與驗收契約見 `docs/plans/2026-08-28-analytics-traffic-integrity-design.md`。

正式部署提交為 `6cef2b2`；`/healthz` 已回 200、`status=ok`、`release=analytics-traffic-integrity-v2`。公開首頁仍維持摘要開放與 0 個結帳連結；未登入不能建立管理預覽狀態，後台 API 仍拒絕未驗證請求。此次正式驗收只讀公開端點，沒有製造需求訊號、建立訂單、寄送通知或操作正式客戶資料。

## 結論

後台新增的是可稽核的需求證據系統，不是用點擊數包裝的銷售預測。系統以第一方匿名工作階段串起仙策詳情、閱讀深度、有效閱讀、匿名意願、傳音、結帳、建單與付款；同一工作階段重複訊號會去重，機器流量與後台預覽不列入判讀。

## 專業判讀規則

- 少於 10 個仙策工作階段：資料不足，不評分、不排序，也不建議改價格。
- 10～29 個：探索級，只呈現現象與下一個驗證動作，不顯示精確分數或領先標記。
- 30～99 個：方向級，可排序下一個實驗，但仍不能宣稱需求成立。
- 100 個以上：穩定級，仍須以實際傳音與付款交叉驗證。
- 固定 7／30／90 日觀察窗，趨勢只和等長前一期比較。
- 公開收款關閉時，不把零結帳或零付款當成商品失敗；只使用閱讀、意願與傳音證據。
- 「需求證據指數」只用於六策內部排序，不是成交率或購買機率。

## 已實作

- PostgreSQL／SQLite 共用的事件版本、事件值、匿名工作階段、HMAC 去重鍵、機器標記與頁面路徑欄位。
- 仙策詳情的 50%／90% 閱讀與 45 秒可見閱讀訊號。
- 收款關閉時的「我想取得這一策」匿名意願入口，不建立訂單、不要求 Email。
- 傳音 CTA、實際傳音、建單與付款事件可沿同一匿名工作階段歸因。
- 後台六策漏斗、信心等級、證據指數、等長趨勢、瓶頸依據、下一步與資料品質摘要。
- 原「瀏覽轉換率」改成近 30 日不重複工作階段付款轉換；收款關閉時顯示破折號與原因，不顯示失真百分比。
- 事件只存粗粒度來源，不保存完整 referrer、UTM 字串、IP、Email、姓名、留言正文或付款資料。

## 失敗保護

- 事件失敗不阻擋公開頁閱讀、傳音或付款主流程。
- 伺服器只接受事件與事件值白名單，並由伺服器判斷來源；客戶端不能自行提交任意來源分類。
- 管理介面只用 `textContent` 建立資料內容，不把事件值插入 HTML。
- 既有資料以加法遷移保留；沒有刪除歷史事件，也沒有啟用未經核准的資料自動刪除政策。
