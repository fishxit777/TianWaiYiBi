# 仙策需求雷達 V1・可稽核決策系統設計

日期：2026-08-27

## 決策摘要

需求雷達不做黑箱 AI 預測，也不以原始點擊數直接判定市場需求。系統採第一方事件、匿名工作階段去重、固定歸因時間窗、前期對照、樣本門檻與可解釋規則，輸出的是「需求證據」而不是成交保證。

## 真正問題

既有後台能顯示瀏覽、來源、訂單與累計轉換，但仍有四個決策缺口：

1. 篩選事件未保存選項，無法辨認客戶關心的問題類型。
2. 沒有閱讀深度與明確意願事件，付款關閉時會把「零付款」誤解成「零需求」。
3. 既有轉換率以所有頁面事件為分母，沒有仙策別、工作階段去重或樣本可信度。
4. 固定文案式判斷若不揭露樣本與依據，容易製造錯誤確定性。

## 方案比較

### A. 數字卡＋固定 if

開發最快，但重複瀏覽、機器流量與小樣本會直接污染判斷；拒絕採用。

### B. 外接 GA／大型資料倉儲

功能完整，但增加第三方追蹤、Cookie、維護與學習成本；目前六個仙策與驗證期規模不值得。

### C. 第一方可稽核漏斗（採用）

沿用 Flask、Neon PostgreSQL 與既有 `analytics_events`，加入事件版本、事件值、粗粒度頁面、機器流量旗標、去重鍵與訂單工作階段歸因。後台以 SQL 聚合六個仙策的目前／前期漏斗，再由純函式產生信心等級、診斷證據與下一步。

## 事件字典 V1

| 事件 | 意義 | 去重 |
| --- | --- | --- |
| `page_view` | 進入首頁 | 同工作階段、同日 |
| `view_idea` | 進入特定仙策詳情 | 同工作階段、同仙策、同日 |
| `reading_depth` 50／90 | 有效閱讀至指定深度 | 同工作階段、仙策、門檻 |
| `engaged_read` | 頁面可見且停留達 45 秒 | 同工作階段、仙策 |
| `filter_used` | 使用六脈需求篩選，保存實際分類 | 同工作階段、分類、同日 |
| `interest_registered` | 收款關閉時主動表示想取得此策 | 同工作階段、仙策 |
| `conversation_cta_clicked` | 主動開啟該策傳音區 | 同工作階段、仙策、同日 |
| `conversation_submitted` | 傳音實際建立成功 | 每則訊息一次 |
| `checkout_opened` | 進入結帳頁 | 同工作階段、仙策、同日 |
| `order_created` | 訂單建立成功 | 每筆訂單一次 |
| `purchase_completed` | 金流伺服器確認付款 | 每筆付款事件一次 |

瀏覽器不得自行指定任意事件或任意值。來源由伺服器歸類為 direct、web、line、search、social、email、referral 或 admin-preview；不保存完整 referrer、UTM、IP 或 User-Agent，只保存粗分類與是否疑似自動化。

## 漏斗與歸因

管理員可切換 7／30／90 日。每個視窗同時比較緊鄰的等長前期。各階段一律以不重複匿名工作階段計算；訂單保存建立當下的匿名工作階段，付款 webhook 才能回接原始漏斗，而不是用 Email 或客戶姓名追蹤。

漏斗順序：詳情訪客 → 50% 閱讀 → 90%／45 秒有效閱讀 → 意願／傳音 → 結帳 → 建單 → 付款。

「需求證據指數」只用來排序六策，不是成交率預測。指數以「各階段不重複工作階段 ÷ 詳情有效訪客」標準化，不用原始點擊數堆高分數。正式收款關閉時：觸及 20%、50% 閱讀 20%、有效閱讀 20%、主動意願 25%、實際傳音 15%；正式收款開啟時才納入結帳、建單與付款，權重合計 100%。

## 信心與診斷規則

- 少於 10 位仙策訪客：`資料不足`，只允許建議繼續收集。
- 10～29 位：`探索級`，可指出現象，不可宣稱需求成立。
- 30～99 位：`方向級`，可提出優先改善方向。
- 100 位以上：`穩定級`，仍須配合實際詢問與付款證據。

每條診斷都必須回傳：規則代碼、觀察值、分母、信心、可執行動作。付款關閉時不得用零結帳或零付款指責商品；只能依閱讀、意願與傳音判斷前置需求。

## 資料品質與失敗模式

- `admin-preview` 與疑似 bot／監控流量排除於需求計算，但保留總數供資料品質稽核。
- 舊事件缺少工作階段或版本時列為 legacy，不補造推論。
- 網路中斷不阻擋閱讀與留言；追蹤失敗靜默降級，不影響主要功能。
- 前端重送透過伺服器去重鍵冪等；付款仍以既有金流 webhook 為唯一真相。
- 原始事件暫不自動刪除；建立保存期限屬資料刪除政策，需另行明確授權。現階段事件不含直接身分資料。

## 非功能需求

- 後台聚合只掃描選定視窗與前一期，利用 `(idea_id, event_name, created_at)`、`(session_id, created_at)` 與訂單歸因索引。
- SQLite 與 PostgreSQL schema／additive migration 同步；既有正式資料不可重建或刪除。
- 所有計算為可單元測試的純函式；空資料、小樣本、機器流量、付款開關與完整漏斗均須測試。
- 正式驗收不得建立訂單、送出留言、操作 Passkey、復原碼或客戶權限。

## ADR-001：以第一方事件漏斗取代外部分析與黑箱預測

### 狀態

Accepted

### 決定

在既有單體應用與 PostgreSQL 內完成事件收集、聚合與可解釋診斷。雷達輸出需求證據、信心與建議，不輸出無法校準的購買機率。

### 正面結果

- 不新增第三方追蹤與月費。
- 可由資料庫重算、由測試重現、由管理員閱讀依據。
- 付款關閉時仍能以明確意願訊號驗證商品。

### 代價

- 不具備跨裝置身分拼接。
- 初期樣本少時多數結果會誠實顯示資料不足。
- 規則需在取得實際購買資料後重新校準。
