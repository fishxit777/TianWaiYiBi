# V26 客戶訊息通道退役設計

日期：2026-08-30  
狀態：已由專案負責人確認

## 目的

完整退役公開留言、客服引導、私人 LINE 人工接手與客戶 LINE Bot 指令，避免網站同時存在多套訊息入口與混亂文案。這次不是重新設計客服，而是縮小產品邊界；「傳音脈」仍是六脈分類之一，與傳訊功能無關，名稱與內容都保留。

## 已確認的合格標準

1. 移除所有公開客服、留言、傳音服務與私人 LINE 人工入口，包括導覽、頁尾、`/transmission`、QR／連結、客戶 LINE 指令、前後台程式、API、CSS 與相關文案；不新增客服小幫手。
2. 清除留言殘留：移除 `section_messages` 的新建表、啟動遷移、舊 Turnstile action 與死樣式；正式歷史資料表先凍結、不破壞性刪除，保留「相關路由必須回 404」的防回歸測試。
3. 保留管理員 LINE 營運／安全推播、客戶交易信及「傳音脈」內容分類；公開收款繼續關閉。完成後須測試、機密檢查、文件、commit、push、正式驗證及同步核對。

## 方案比較

### 方案 A：只隱藏畫面

保留 `/transmission`、LINE webhook、模擬器、資料表與遷移，只從導覽隱藏入口。改動最小，但仍有可直接呼叫的服務、維護成本與誤開風險，不符合「全部取消」。

### 方案 B：連正式歷史資料一起硬刪

移除程式並在正式 PostgreSQL 執行 `DROP TABLE`。表面最乾淨，但屬不可逆破壞，無助於公開面退役，也違反既有驗收資料不得破壞的原則。

### 方案 C：完整退役執行面，凍結歷史資料（採用）

移除公開入口、客戶 LINE webhook／指令／模擬器、客服素材、留言與客戶 LINE 的 schema 建立及啟動遷移；新環境不再建立 `section_messages` 或 `line_events`。正式資料庫若已有舊表則保持原狀，應用程式不讀、不寫、不升級，也不在本次執行任何刪表。管理員 LINE 推播仍由獨立通知模組發送，交易信仍由郵件模組發送。

這個方案同時滿足最小產品邊界、可驗證退役與非破壞性資料處理，因此採用。

## 實作邊界

### 移除

- 公開 `/transmission` 頁面、導覽與頁尾入口、LINE 加好友連結、QR 與傳音頁專用圖片。
- 客戶 LINE webhook、follow／文字指令、Flex 目錄回覆、本機 LINE 模擬器與相關測試。
- `section_messages`、`line_events` 的新建 schema、啟動遷移、跨資料庫遷移清單與索引建立。
- `public-conversation` Turnstile action、留言後台與公開留言的死 CSS。
- 付款狀態頁中要求聯絡客服的文案，改成不承諾人工接手的安全自助指引。

### 保留

- `tianwai.notifications` 的管理員 LINE 每日摘要、營運與安全告警、重試佇列。
- 付款完成、開通與退款等客戶交易信。
- 「傳音脈」分類、篩選、後台分類與相對應 Q 版仙人內容。
- 公開收款關閉機制與所有既有付款安全限制。
- 舊路由 404 防回歸測試，以及正式資料庫既有歷史表的原始狀態。

## 驗證方式

- 本機與正式站確認 `/transmission`、`/line/webhook`、`/dev/line`、既有公開／後台 conversation API 全部回 404。
- 公開首頁、內容頁、結帳頁不含客服、訂單協助、LINE 加好友、QR 或留言元件。
- 新測試資料庫不建立 `section_messages` 與 `line_events`。
- 管理員 LINE 推播、交易信、六脈分類與公開收款關閉測試維持通過。
- 執行完整測試、程式編譯、機密掃描、本機桌面／手機視覺 QA、正式 `/healthz` 與 main/origin 同步核對。
