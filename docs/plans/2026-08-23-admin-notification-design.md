# 管理員通知系統設計

## 決策

採用「每日三次營運摘要＋高風險事件即時雙通道告警」。摘要於台北時間 08:00、12:00、20:00 觸發；高風險、重大付款／開通／登入／系統事件不等待摘要，立即分別送往管理員 LINE 與 Gmail。任何一個通道失敗，不阻擋另一個通道，並在通知佇列保留失敗原因與重試紀錄。

## 真正目標與限制

- 目標不是把所有資料都推送，而是讓唯一管理員能快速判斷「現在正常嗎、出了什麼事、要先處理什麼」。
- Render 免費 Web Service 可能休眠，Gunicorn 又有多個 worker，因此不能依賴程序內排程器；否則可能漏送或重複送。
- 外部通知不得包含完整 Email、完整 IP、驗證碼、登入碼、Cookie、Token、金流密鑰或郵件密碼。
- GitHub Actions 排程可能有數分鐘延遲；08:00／12:00／20:00 是觸發時段，不承諾精確到秒。

## 評估過的方案

1. **Flask 程序內排程**：成本最低，但服務休眠時不執行，多 worker 也可能重複送。淘汰。
2. **Render Cron Job**：架構乾淨，但需新增獨立服務與費用，現階段 ROI 較低。保留為規模化替代方案。
3. **GitHub Actions 呼叫受保護端點**：不依賴 Web 程序常駐、可手動重跑、可用佇列防重送，最符合目前成本與可靠度。採用。

## 通知內容

### 每日營運摘要

每次摘要均含：統計期間、今日訂單與營收、付款／待付款／取消退款、開通與待開通、活躍工作階段與可信裝置、瀏覽與熱門想法、未結風險案件、高／重大事件、封鎖狀態、LINE／Gmail／金流／HTTPS 整合狀態、通知與交易郵件失敗數、證據鏈驗證，以及依優先順序整理的「需要處理」與「正常但值得知道」。

LINE 使用可在單一訊息內讀完的版本；Gmail 使用較完整版本。即使沒有異常，也明確列出正常狀態，避免沉默造成誤判。

### 即時異常告警

包含：嚴重度、白話事件名稱、發生時間、事件／案件編號、匿名客戶代碼、遮罩 IP、路徑、系統已採取動作、風險分數與建議處置。詳細原始資料僅能登入管理後台查看。

## 安全與可靠度

- 排程端點使用至少 32 字元的獨立密鑰，採常數時間比對；不共用管理員密碼、LINE 或金流密鑰。
- 每個日期、時段與通道有唯一防重送鍵；GitHub 重試或人工重跑不會重複推播。
- LINE 與 Gmail 各自建立通知佇列列，個別送出、個別記錄與個別重試。
- 管理員 Gmail 使用獨立 `ADMIN_ALERT_EMAIL`，不得推論或誤用客戶 Email。
- 通知內容集中由隱私清理器生成，避免敏感資訊誤流出。

## 成功標準

- 同一時段重跑不增加重複通知。
- 高／重大風險事件會建立 LINE 與 Gmail 兩筆通知。
- 任一通道失敗時另一通道仍可成功。
- 摘要包含正常狀態、異常狀態及優先處理建議。
- 所有自動化與安全測試通過，正式健康檢查能辨識新版本。
