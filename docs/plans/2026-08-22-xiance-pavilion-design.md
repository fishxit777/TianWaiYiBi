# 天外一筆・仙策閣初版設計

日期：2026-08-22

## 直接結論

初版採用「天外一筆工作室」母品牌下的獨立產品「仙策閣」：把每個想法包裝成一位具備不同專長的原創修仙角色與一套可付費解鎖的心法。產品不模仿《航海王》人物、美術或名稱，只保留「每位角色有獨特能力、共同組成世界觀」這個抽象機制。

技術採 Flask 模組化單體、SQLite、原生 HTML/CSS/JavaScript。這是目前最高 ROI：本機即可完整展示官網、想法商城、付款流程、LINE Bot 邏輯、後台數據與安全紀錄；未來可逐步替換成 PostgreSQL、正式金流與 LINE Messaging API，不需重寫產品核心。

## 真正問題與目標

- 真正問題：想法目前只是零散靈感，客戶看不懂差異、價值與購買後會得到什麼。
- 真正目標：把想法變成可比較、可付款、可交付、可追蹤成效的數位商品。
- 最大限制：需求尚未驗證，正式金流與大量內容製作都不應先投入。
- 初版成功標準：使用者能看懂六種能力差異、選擇一個想法、完成本機模擬付款並取得內容；管理者能看訂單、營收、安全事件並一次調整全部價格。

## 方案比較

1. Flask＋SQLite 模組化單體（採用）
   - 優點：本機可驗證、依賴少、維護成本低、與萬語通既有 Flask 經驗相容。
   - 缺點：正式高流量前需換 PostgreSQL，背景工作也需獨立佇列。
2. Next.js＋Supabase
   - 優點：雲端部署與即時資料方便。
   - 缺點：初版即依賴外部帳號，資料與權限面更複雜。
3. LINE、Web、金流、後台拆成微服務
   - 優點：長期隔離性與獨立擴張較好。
   - 缺點：目前沒有流量證據，會過早增加維護與失敗點。

## 產品與視覺

- 母品牌：天外一筆工作室
- 產品名：仙策閣
- 主標：靈感入世，萬法成案
- 說明：想法販售・創意支援
- 視覺方向：玄夜卷軸、雲海、星圖、朱砂筆觸、玉色靈光；以深墨、月玉、朱砂、舊金為主色。
- 記憶點：每張想法卡是一位不同修士的「命牌」，卡片上的單字印記與技能定位一眼可辨。

初版六位原創角色：

1. 破局劍修：切開問題、聚焦最小可行解。
2. 造境符師：建立品牌世界觀與視覺敘事。
3. 增長丹師：把內容與優惠煉成可測試的轉換配方。
4. 機關偃師：設計自動化流程與 AI 槓桿。
5. 回聲樂修：建立社群、內容節奏與回訪機制。
6. 觀星策士：分析趨勢、競品與機會窗口。

每項商品都有免費可見的摘要、適用對象、能力說明，以及付款後才顯示的完整心法。全站初始統一價格為 NT$199；訂單保存成交價快照，日後調價不影響舊訂單。

## 架構與資料流

```text
官網／Web App ─┐
LINE webhook ──┼─> Flask 應用服務 ─> SQLite
管理後台 ──────┘        │
                         ├─> PaymentAdapter（初版本機模擬）
                         └─> LINE Reply API（有憑證才啟用）
```

主要資料表：ideas、settings、orders、payment_events、analytics_events、line_events、admin_sessions、admin_login_attempts、security_events、blocked_ips、audit_logs。

付款流程：建立 pending 訂單 → 付款介面 → webhook／模擬支付事件 → 驗證簽章、事件 ID、金額、訂單狀態 → 單一交易內標記 paid → 以 HMAC 派生的高熵 access token 解鎖內容，資料庫只保存 token 雜湊。重複 webhook 只回報已處理，不重複入帳。

LINE 流程：官方 webhook 在設定 secret 後才接受事件；先驗 `X-Line-Signature`，再以 webhook event ID 防重送。未設定正式憑證時只啟用本機模擬器，不會對外送訊息。

## 安全設計

- 管理員密碼只讀環境變數；不寫入專案、資料庫或日誌。
- 管理 session 使用 256-bit 隨機 token；資料庫只存 SHA-256 雜湊，Cookie 為 HttpOnly、SameSite=Strict、限 `/admin`。
- 管理變更均驗證 CSRF，寫入 audit_logs。
- 管理登入採速率限制與暫時 IP 封鎖，訊息不揭露帳號是否存在。
- 支援管理 IP allowlist 與 session 綁定 IP；正式環境可強制開啟。
- 所有 SQL 皆參數化；輸入有長度、格式與白名單驗證。
- 安全標頭包含 CSP、frame denial、nosniff、Referrer-Policy、Permissions-Policy；HTTPS 時啟用 HSTS。
- 探測 `.env`、`.git`、`wp-admin`、路徑穿越與常見注入片段時拒絕並記錄，日誌不保存 Cookie、token、付款秘密或訊息全文。
- 正式金流 webhook 必須驗簽、核對金額與防重送；客戶端不得直接把訂單改為 paid。

## 錯誤處理與測試

- 使用者錯誤回傳可理解的繁體中文，不暴露堆疊或資料庫細節。
- 支付金額不符、簽章錯誤與重複事件有獨立測試。
- 管理未登入、CSRF 錯誤、連續登入失敗與敏感路徑掃描有安全測試。
- 公開頁、商品詳情、結帳、解鎖、LINE 簽章與後台 API 皆以 Flask test client 驗證。
- 最後用本機瀏覽器檢查桌機與手機寬度，確認無水平捲動、文字截斷、按鈕不可點或對比不足。

## 主要假設與未知

- 假設初始統一價格 NT$199；後台可隨時修改。
- 假設數位內容以一次買斷為主，而非訂閱。
- 假設先驗證六個想法，未驗證前不大量擴充角色與內容。
- 未知正式支付供應商、退款規則、發票流程、LINE 官方帳號憑證與正式網域；初版均保留介面但不擅自接線。

## 最大風險與反向思考

最大風險不是技術，而是「客戶願不願意為純想法付費」。最可能的失敗方式是內容看起來像一句靈感，購後落差太大。因此每個商品必須清楚說明交付物，並用少量真實流量先測點擊、結帳啟動與付款率。若轉換低，優先把商品改成「想法＋可執行模板／清單／示例」，而不是先增加更多角色。
